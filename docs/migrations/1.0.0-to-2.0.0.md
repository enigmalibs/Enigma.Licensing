# Prompt part — migrate a consumer from Enigma.Licensing 1.0.0 to 2.0.0

*Reusable block. Paste into a prompt for any repository that references `Enigma.Licensing` 1.x.*

---

## Task

Upgrade this repository's `Enigma.Licensing` package reference from **1.0.0 to 2.0.0** and update every
call site the major release breaks. This is an **API migration, not a licensing-policy review**: do not
change signature algorithms, key sizes, validity windows, product identifiers or device binding while
migrating. Do not add compatibility wrappers that re-create the 1.x shape — adopt the new shape.

## What breaks — and this is the only thing that breaks

2.0.0 has exactly one breaking theme: **feature flags and claims are gone.** Nothing in the library ever
decided anything from them. The validator's check order is envelope → format → algorithm → signature →
payload → validity window → product identifier → device identifier, and it stops there; `Features` and
`Claims` were signed, stored, displayed and documented while no check ever read them.

Five public members were **deleted outright**:

| 1.0.0 (removed) | Was |
|---|---|
| `License.Features` | `IReadOnlyCollection<string>` |
| `License.Claims` | `IReadOnlyDictionary<string, string>` |
| `License.HasFeature(string)` | `bool` |
| `LicenseRequest.Features` | `IReadOnlyCollection<string>?` |
| `LicenseRequest.Claims` | `IReadOnlyDictionary<string, string>?` |

Nothing is `[Obsolete]`, there are no shims and no transitional overloads, so 1.x call sites **fail to
compile rather than warn**. That is the detection mechanism for this migration: **the build error list is
the to-do list.** Work it to zero.

## What does *not* change — read this before hunting for work

- **Every licence issued by 1.0.0 stays valid. No file is reissued, converted or re-signed.** A 1.0.0
  payload carries `"features"` and `"claims"`; a payload member 2.0.0 does not know is **ignored**, not
  rejected. Nothing ever re-serializes a licence in order to check one — the founding invariant of the
  format — so the signature still covers exactly the bytes it was made over. The two fields simply stop
  surfacing on `License`.
- **The break has no runtime component at all.** If it compiles, it behaves as it did.
- **Both document formats are unchanged**: `enigma-license/1` and `enigma-key/1`, same fields, same
  encodings, same `keyId` construction. Key files do not move.
- **All six signature schemes behave as before** — `RsaSha256`, `RsaSha384`, `RsaSha512`, `MLDsa44`,
  `MLDsa65`, `MLDsa87` — including the rule that the verifier is chosen from the *envelope's* `algorithm`.
- **The check order and all seven `LicenseFailure` reasons are unchanged**, as is the rule that validation
  returns a verdict rather than throwing while a bad *key* file throws.
- **The error contract is unchanged**, and so is the "only Enigma.Licensing types on the public surface"
  guarantee.
- **The target frameworks are unchanged**: `netstandard2.0`, `net8.0`, `net10.0`.
- `ILicenseGenerator`, `ILicenseValidator`, `ILicenseStore`, `IKeyService`, `LicenseEnvelope`,
  `LicensingKey`, `DeviceIdentifier` and `AddEnigmaLicensing()` are otherwise **untouched**.

## Step 1 — bump the reference

Set the `Enigma.Licensing` version to `2.0.0` (in `Directory.Packages.props` if the repository uses
Central Package Management, otherwise on each `<PackageReference>`), restore, then build to enumerate the
breaks.

Dependency changes, so you know what you do *not* have to touch:

- `Enigma.Core` stays at **2.0.0**; `Ulid` at 1.4.1, `DeviceId` at 6.11.0, `System.Buffers` at 4.6.1.
- `Microsoft.Extensions.DependencyInjection.Abstractions` stays on its **9.x** floor — deliberately, so
  the package does not drag your `Microsoft.Extensions.*` set forward.
- `System.Text.Json` moves **10.0.10 → 10.0.12**, on `netstandard2.0` only, where it is not
  framework-provided. A servicing patch; nothing else in the graph moves.
- No dependency was added or removed.

## Step 2 — issuing: drop the two initializers

```csharp
// 1.0.0 — no longer compiles
var request = new LicenseRequest
{
    ProductId = "MyApp 2.0",
    Owner = "Acme GmbH",
    Features = new[] { "export-pdf", "team-sync" },
    Claims = new Dictionary<string, string> { ["seats"] = "25" },
};

// 2.0.0
var request = new LicenseRequest
{
    ProductId = "MyApp 2.0",
    Owner = "Acme GmbH",
};
```

Every other member of `LicenseRequest` — `ProductId`, `Owner`, `DeviceId`, `ValidFrom`, `ValidUntil`,
`Id`, `CreatedAt` — is unchanged, as is every `ILicenseGenerator` overload.

## Step 3 — checking: replace the reads

```csharp
// 1.0.0 — no longer compiles
if (result.IsValid && result.License is { } license)
{
    bool canExport = license.HasFeature("export-pdf");
    int seats = int.Parse(license.Claims["seats"]);
}

// 2.0.0 — a valid licence is a valid licence; entitlements are your application's own concern
if (result.IsValid)
{
    // gate on whatever your application already uses — a plan name, a product identifier, your own
    // entitlement service — not on data the licence signs but never validates
}
```

**Do not reimplement features and claims on top of what remains.** Encoding a feature list into
`ProductId`, `Owner` or the device identifier is worse than the members that were removed: those fields
*are* validated, so a value crafted to carry entitlements changes what the licence matches. If your
application genuinely needs per-feature entitlement, that is a mechanism of its own — not a field smuggled
through a licence.

If you need a licence to distinguish tiers, the supported way is a **distinct product identifier per
tier**, matched with the anchored `*` wildcard the validator already supports — `"MyApp Pro 2.*"` against
`"MyApp Pro 2.4"`.

## Step 4 — anything that stored or displayed the two fields

Search for `Features`, `Claims` and `HasFeature` across the repository, not only in code:

- **Serialized application state** — a saved form, a settings file or a database column that mirrored a
  licence's features or claims. Drop the field; a document that still carries it is read fine, because an
  unknown member is ignored.
- **UI** — any panel, table or report that listed a licence's features or claims.
- **Logs and support tooling** — anything that printed them when diagnosing a customer's licence.
- **Your own documentation** — the two concepts are gone from the library's guides; make sure yours agree.

## Step 5 — verify

1. Build to zero errors. There should be no warnings introduced by the upgrade: the removed members were
   deleted, not deprecated, so nothing survives as an obsolete-member warning.
2. Run your test suite. Any test that asserted on a feature flag or a claim is asserting on an API that no
   longer exists — delete it rather than adapting it; there is nothing left for it to guard.
3. **Validate a licence issued under 1.0.0 against the same public key.** It must still reach
   `LicenseFailure.None`. This is the one behaviour worth confirming with a real file rather than trusting
   a release note, and it is the evidence that no reissue is needed.

## What you should *not* do

- Do not reissue, convert or re-sign existing licences. They are valid.
- Do not regenerate key pairs. `enigma-key/1` did not change.
- Do not add an extension method, wrapper record or adapter that restores `HasFeature`/`Claims` over
  `License`. The data is not on the type any more, and reading it back out of the raw payload would mean
  parsing a document the validator has already parsed — and trusting a field nothing validates.
- Do not change `JsonUnmappedMemberHandling` anywhere near a licence payload. Ignoring unknown members is
  exactly what keeps 1.0.0 licences valid.
