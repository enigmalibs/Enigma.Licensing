# BUG-5147 — Centre page content at wide widths

**Status:** DONE
**Type:** single-phase
**Branch:** `bugfix/bug-5147-centred-pages`
**Run:** vibe/2026-09-11-core-2-centering

## Objective

In the desktop app, a page's content is pinned to the **left** edge of the content area once the window
is wider than the content's measure, leaving a growing band of empty space on the right. Centre it
instead, so a wide or maximised window puts the page in the middle of the area beside the navigation
rail.

## Context & constraints

All four pages have the same shape — `ScrollViewer` → `StackPanel Classes="page"` — and the whole of
the page's layout contract is one style in `src/Enigma.Licensing.Desktop/App.axaml`:

```xml
<Style Selector="StackPanel.page">
  <Setter Property="Margin" Value="24" />
  <Setter Property="Spacing" Value="16" />
  <Setter Property="MaxWidth" Value="880" />
  <Setter Property="HorizontalAlignment" Value="Left" />
</Style>
```

So this is not an accident of a container somewhere: `HorizontalAlignment="Left"` is the setter being
complained about, and `MaxWidth="880"` is what makes it visible — without the cap the panel would fill
the area and alignment would never come into play.

The fix must hold at **both** ends of the window's width range. The window's `MinWidth` is 760 and the
rail takes 90, so the content area starts around 670 — narrower than the 880 cap — and at that size the
page must still take the full width it can get, with no horizontal scrolling introduced.

## Decisions

1. **`HorizontalAlignment="Stretch"`, keeping `MaxWidth="880"`.** Avalonia arranges a `Stretch`-aligned
   element at the *centre* of the space it was given whenever a constraint — here `MaxWidth` — stops it
   filling that space, which is exactly the wanted behaviour: full width below 880, centred above it.
   **`Center` is the wrong tool** even though it sounds like the right one: a `Center`-aligned element is
   arranged at its *desired* width, which for this panel is whatever its widest child asked for, so the
   settings cards would stop filling the 880 and the page would visibly narrow instead of centring.
   The Avalonia arrange behaviour is verified with a throwaway layout probe before the change is
   committed — not assumed from the documentation.
2. **`MaxWidth` stays 880.** The report is about alignment, not about measure, and 880 is a deliberate
   reading width for a settings-card page.
3. **One style, not four views.** The class exists so a page's frame is decided once; changing it there
   fixes all four pages — including any later one — and keeps the views free of layout constants.
4. **No layout regression test.** The desktop suite deliberately stands up no Avalonia platform, and
   measuring or arranging a real page would need one; adding a headless-Avalonia dependency for a single
   setter is infrastructure this repository has consciously gone without. The probe of decision 1, the
   zero-warning build and the `AVLN` check are the evidence, and both are recorded in the completion doc.

## Steps

1. Prove the arrange behaviour of decision 1 with a throwaway Avalonia layout probe in the session
   scratchpad (measure and arrange a `StackPanel` carrying `MaxWidth` under both `Stretch` and `Center`
   inside a wider rect, and read back `Bounds`). Nothing from the probe is committed.
2. In `App.axaml`, set `StackPanel.page`'s `HorizontalAlignment` to `Stretch` and add a comment saying
   why that value and not `Center` — the next reader will otherwise "fix" it back.
3. Build the desktop project in Release (zero warnings) and confirm its `AVLN` count is still 0 — a XAML
   warning does not fail the build on its own, so it is checked by hand.
4. Run the whole test suite: the change touches no ViewModel, so the 298 desktop cases and the 866
   library ones must be unaffected.
5. Documentation sweep: `CLAUDE.md`'s desktop sections carry the app's layout decisions, so the page
   frame's alignment belongs there with the rest.

## Acceptance criteria

1. `StackPanel.page` is `HorizontalAlignment="Stretch"` with `MaxWidth="880"`, and the reason `Center`
   was not used is written next to it.
2. The probe shows a `Stretch`-aligned, `MaxWidth`-capped panel arranged centred in a wider rect
   (offset `(available − 880) / 2`, width 880), and the same panel under `Center` arranged at its
   children's desired width — the evidence for both halves of decision 1, quoted in the completion doc.
3. `DOTNET_ROOT=~/.dotnet dotnet build Enigma.Licensing.slnx -c Release` succeeds with zero warnings,
   and `... dotnet build src/Enigma.Licensing.Desktop/... -v normal | grep -c AVLN` prints 0.
4. `DOTNET_ROOT=~/.dotnet dotnet test --solution Enigma.Licensing.slnx -c Release` is green.
5. Nothing else about the pages moves: no view file changes, and `MaxWidth`, `Margin` and `Spacing` are
   as they were.

## Out of scope

- The content width itself, the rail's `PaneSize`, and the window's default or minimum size.
- Per-page layout (a page that wants a different frame would be its own decision).
- Vertical centring, and any change to the `ScrollViewer`s.
