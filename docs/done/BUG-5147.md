# BUG-5147 — Centre page content at wide widths

**Branch:** `bugfix/bug-5147-centred-pages`
**Status:** DONE

## Summary

The desktop app's pages are each a `ScrollViewer` over a `StackPanel Classes="page"`, and that class —
`Margin 24`, `Spacing 16`, `MaxWidth 880` — carried `HorizontalAlignment="Left"`. Past 880 of available
width the page therefore stayed pinned against the navigation rail and the surplus piled up on the
right, which is what a maximised window on a wide monitor made obvious. The alignment is now
**`Stretch`**: one setter in `App.axaml`, no view file touched, all four pages fixed at once.

`Stretch` rather than `Center` is the substance of the fix, and it is counter-intuitive enough to have
been measured rather than assumed. Avalonia arranges a `Stretch`-aligned element at the width it was
offered and then centres it when a constraint — here `MaxWidth` — stopped it filling that width; a
`Center`-aligned element is arranged at its *desired* width instead, which for a stack of settings
cards is whatever the widest card happened to ask for. `Center` would therefore have centred the page
and narrowed it in the same stroke, with the cards no longer reaching the 880 they are laid out for.

A throwaway Avalonia probe (measure, arrange, read `Bounds` back) settled both halves, using the real
numbers — an 880 cap over a child wanting 400:

```
available width = 1400, MaxWidth = 880, child desired width = 400
Left     desired=   400 bounds.X=     0 bounds.Width=   400
Center   desired=   400 bounds.X=   500 bounds.Width=   400
Stretch  desired=   400 bounds.X=   260 bounds.Width=   880

available width = 670 (the narrowest content area: MinWidth 760 - rail 90), MaxWidth = 880
Left     desired=   400 bounds.X=     0 bounds.Width=   400
Center   desired=   400 bounds.X=   135 bounds.Width=   400
Stretch  desired=   400 bounds.X=     0 bounds.Width=   670
```

`Stretch` at 1400: x = (1400 − 880) / 2 = 260, width 880 — centred and filling the cap. `Stretch` at
670: x = 0, width 670 — the full content area, nothing centred, nothing overflowing, so the narrow end
of the window's range is unaffected. The probe lived in the session scratchpad and is not committed; its
numbers are quoted in the comment beside the setter, which is where the next reader will look before
"correcting" `Stretch` to `Center`.

## Deviations & follow-ups

- **No deviation from the plan.** The probe confirmed decision 1 exactly as the plan predicted it
  would, so nothing had to be adapted.
- **`MaxWidth`, `Margin` and `Spacing` were deliberately left alone.** The report was about alignment,
  and 880 is a deliberate reading measure for a settings-card page. A future decision to widen it is
  its own item.
- **A page that wants a different frame is still free to have one** — nothing here moved layout into a
  view, so the class remains the only place a page's measure and position are decided.
- **Not verified by eye in a running window.** The evidence is the probe's arrange numbers plus a clean
  build; opening the app would have needed a human to look at it, and the suite stands up no platform.
- **Line endings:** no CRLF churn in this dev (recommendation-only, per the workflow — no action taken).

## Decisions taken at build time

| Question | Chosen | Why |
|---|---|---|
| Probe or trust the documentation? | Probe — a throwaway console project against Avalonia 12.1.1 | The `Stretch`-centres / `Center`-shrinks asymmetry is the entire fix; being wrong about it would have shipped a page that narrows instead of centring, and measuring it cost two minutes |
| Probe the narrow end too? | Yes, at 670 (`MinWidth` 760 − rail 90) | The fix has to hold at both ends of the window's range; the number proves no centring and no overflow where the content area is narrower than the cap |
| Where the explanation lives | A comment above the style, with the measured numbers | A bare `Stretch` reads like an oversight next to a `MaxWidth`, and the obvious "fix" is the wrong value. The numbers make the comment checkable rather than a claim |
| Also note it in `CLAUDE.md`? | Yes, one *Shipped* entry | The repo keeps the app's layout decisions there, and this one carries a "do not change it back" |
